# История обучения и постановки задачи

## 1. От общей релевантности к пяти темам

Первый вариант BERT решал бинарную задачу:

```text
text -> relevant
```

Эта постановка показывала, относится ли пост хотя бы к одному из сигналов Банка России, но не отвечала на вопрос, к какому именно сигналу. Для курсовой этого оказалось мало: нужно измерять распространение отдельных смыслов.

Поэтому финальная topic model перешла к пяти меткам:

```text
t1_relevant, t2_relevant, t3_relevant, t4_relevant, t5_relevant
```

## 2. Multi-label вместо binary/multi-class

Один Telegram-пост может одновременно поддерживать несколько тем. Поэтому задача не multi-class, а multi-label:

- на выходе пять независимых logits;
- после logits применяется sigmoid;
- loss - `BCEWithLogitsLoss`;
- threshold подбирается отдельно для каждой темы.

## 3. `relevant` как служебный OR-индикатор

Колонка `relevant` была отделена от BERT-target:

```text
relevant = OR(t1_relevant..t5_relevant)
```

Она нужна для фильтрации, сводной статистики и проверки того, есть ли у поста хотя бы одна тема. Но финальная topic model не учится предсказывать `relevant` отдельной головой.

## 4. Два типа негативов

В корпусе появились два разных источника `relevant=0`:

| Тип | Условие | Надёжность |
|---|---|---|
| Жёсткие негативы | `annotated=True`, `relevant=0` | проверены разметкой |
| Слабые негативы | `annotated=False`, `relevant=0` | отсеяны prefilter-ом |

Слабые негативы увеличивают объём отрицательных примеров, но могут содержать пропущенные релевантные посты. Это методологически важно для интерпретации качества.

## 5. Режим `weak_negatives`

Чтобы использовать дополнительные негативы без чрезмерного доверия к ним, был введён режим `weak_negatives`: `annotated=False` строки добавляются в train с пониженным весом.

В сохранённом topic config:

```json
{
  "data_mode": "weak_negatives",
  "weak_negative_weight": 0.2
}
```

Validation и clean-test при этом должны оставаться на `annotated=True`.

## 6. `sample_weight` и `pos_weight`

В обучении учитывались два разных веса:

- `sample_weight` - понижает вклад слабых негативов;
- `pos_weight` - компенсирует дисбаланс положительных примеров по темам.

Из-за сильного дисбаланса raw `pos_weight` может быть слишком агрессивным, поэтому рабочим режимом стал:

```text
POS_WEIGHT_MODE = "sqrt"
```

В конфиге также есть cap:

```text
pos_weight_cap = 15.0
```

## 7. Dynamic padding и экономия памяти

В BERT-ноутбуках используется dynamic padding через `DataCollatorWithPadding`. Это уменьшает лишние pad-токены в батчах и помогает запускать обучение на Kaggle/Colab GPU.

`MAX_LENGTH=512` оставлен как верхняя граница, потому что Telegram-посты могут быть длинными.

## 8. Выбор checkpoint-а

Лучший checkpoint topic model выбирался по:

```text
macro_pr_auc
```

Это лучше, чем выбирать по F1 при фиксированном threshold 0.5, потому что итоговые thresholds подбираются отдельно после обучения.

Для direction model основной критерий:

```text
macro_f1
```

## 9. Подбор thresholds

После обучения topic model thresholds подбирались на validation отдельно для каждой темы. Сохранённые значения:

```json
{
  "t1_relevant": 0.8,
  "t2_relevant": 0.35,
  "t3_relevant": 0.75,
  "t4_relevant": 0.8,
  "t5_relevant": 0.95
}
```

Thresholds применяются только после sigmoid. Test используется для финальной оценки, а не для подбора.

## 10. `test_clean` и `test_full`

Из-за слабых негативов оценку нужно разделять:

- `test_clean`: только `annotated=True`, подходит для честной оценки модели;
- `test_full`: содержит слабые негативы, полезен для диагностики поведения на полном распределении, но метрики могут быть искажены шумом.

## 11. Source-wise evaluation

В корпусе есть колонка `source`, показывающая, из какой вырезки пришёл пост (`7days`, `7days2`, `5days`, `dec15`, `apr26`). Source-wise evaluation нужен, чтобы видеть, не переобучилась ли модель на один период или тип разметки.

## 12. Error analysis

После обучения анализировались:

- false positives;
- false negatives;
- per-topic precision/recall/F1;
- source-wise metrics;
- confusion counts;
- отдельные ошибки `t3` и `t4`.

`t3_relevant` и `t4_relevant` оказались особенно сложными по recall, поэтому для inference иногда обсуждалась ручная корректировка thresholds.

## 13. Direction model

После topic model появилась вторая BERT-модель:

```text
[TOPIC=t_i] text -> "+" / "-"
```

Она работает на long-таблице `пост x тема`. Это нужно, потому что один пост может относиться к нескольким темам, а направление влияния может различаться.

## 14. Полный pipeline и ограничение recall

Финальный pipeline:

1. Prefilter выбирает кандидатов.
2. Topic BERT ставит темы `t1..t5`.
3. Direction BERT ставит направление для предсказанных тем.
4. Метрики считаются как на covered pairs, так и в strict-режиме.

Главное ограничение: если topic-stage не создал пару `пост x тема`, direction-stage уже не может её исправить. Поэтому strict-метрики полного pipeline ниже, чем метрики direction model на покрытых парах.

## 15. Ручная корректировка thresholds

Inference notebook читает thresholds из `topic_model_config.json`. Для экспериментов можно вручную снизить пороги, например для `t3_relevant` и `t4_relevant`:

```json
{
  "t3_relevant": 0.05,
  "t4_relevant": 0.05
}
```

Такой шаг повышает recall, но почти наверняка увеличивает false positives. Его нужно фиксировать в отчёте и не смешивать с метриками исходного сохранённого конфига.
